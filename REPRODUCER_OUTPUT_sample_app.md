## Bug 02 — Missing None-check in `update_expense`

**File:** `sample_app/tests/test_bugs.py`
**Tests:**
- `TestBug02UpdateMissingExpense::test_update_missing_raises_value_error`
- `TestBug02UpdateMissingExpense::test_update_missing_does_not_raise_attribute_error`

**Failure output:**
```
AttributeError: 'NoneType' object has no attribute 'title'
  sample_app/api.py:88: in update_expense
      if exp.title is None:
```

**Summary:** `ExpenseTracker.update_expense` calls `self.get_expense(expense_id)`, which returns `None` when the ID is not found. The pre-fix code immediately dereferences `.title` on that `None` value (`if exp.title is None:`) instead of checking whether `exp` itself is `None`. This raises `AttributeError: 'NoneType' object has no attribute 'title'` rather than the intended `ValueError("Expense '...' not found.")`. The test `test_update_missing_raises_value_error` asserts that a `ValueError` matching "not found" is raised and fails because `AttributeError` propagates first. The companion test `test_update_missing_does_not_raise_attribute_error` explicitly catches `AttributeError` and calls `pytest.fail`, making the internal error unambiguous.

## Bug 03 — `over_budget_categories` uses `percent_used > 100` with rounding

**File:** `sample_app/tests/test_bugs.py`
**Tests:**
- `TestBug03OverBudgetBoundary::test_one_cent_over_limit_is_over_budget`
- `TestBug03OverBudgetBoundary::test_exactly_at_limit_is_not_over_budget` *(passes — boundary correct)*

**Failure output:**
```
AssertionError: Spending one cent over the limit must be flagged as over budget
  assert 'food' in []
```

**Summary:** `over_budget_categories` (api.py line 221) filters by `s["percent_used"] > 100`. The `percent_used` field is computed as `round(spent / monthly_limit * 100, 1)`. When spending is $100.01 against a $100 limit, the raw ratio is 100.1% but `round(100.1, 1)` evaluates to `100.0` in Python's banker's rounding. `100.0 > 100` is `False`, so the category is silently excluded from the over-budget list even though `budget_status` itself sets `over_budget: True` (via `remaining < 0`). The test asserts `"food" in over_budget_categories(2024, 5)` when spending is $100.01 and fails because the list is empty. The fix is to use the pre-computed `s["over_budget"]` flag directly instead of re-deriving from `percent_used`.

## Bug 04 — Mutable default argument in `to_csv_rows`

**File:** `sample_app/tests/test_bugs.py`
**Test:** `TestBug04MutableDefaultHeaders::test_mutable_default_can_be_corrupted_externally`

**Failure output:**
```
AssertionError: Default header was corrupted by external mutation: 'id,title'
  (expected 'id,title,amount,category,date,notes')
  assert 'id,title' == 'id,title,amount,category,date,notes'
```

**Summary:** `to_csv_rows` in `utils.py` is declared with `headers: List[str] = []`. Python evaluates default argument expressions once at function-definition time, so every call that omits `headers` shares the same list object. The test retrieves that shared default object via `inspect.signature`, appends values to it (`default_val.extend(["id", "title"])`), then calls `to_csv_rows([e])` without passing `headers`. Because the mutated default is now `["id", "title"]` (truthy), `headers if headers else default_headers` uses it instead of the canonical six-column default, producing the wrong header row `"id,title"`. This proves the bug is exploitable whenever any call site holds a reference to the default and mutates it.

## Bug 05 — `_today_utc` uses UTC clock instead of local clock

**File:** `sample_app/tests/test_bugs.py`
**Test:** `TestBug05UtcDateDefault::test_today_utc_uses_utc_not_local_clock`

**Failure output:**
```
AssertionError: _today_utc() still uses UTC time instead of the local clock.
  Function source:
  def _today_utc() -> str:
      """Return today's date as an ISO-8601 string, based on UTC time."""
      return datetime.now(tz=timezone.utc).strftime("%Y-%m-%d")
```

**Summary:** `main._today_utc()` calls `datetime.now(tz=timezone.utc)`, which returns the current UTC timestamp. For users in UTC+ timezones, the UTC date can lag their local date — e.g., at 01:00 local time (UTC+3), the UTC time is still 22:00 the previous calendar day. An expense added without an explicit `--date` is therefore recorded with yesterday's date. The test inspects the function's source code and asserts that the `timezone.utc` sentinel is absent; the assertion fails because the sentinel is present, directly confirming that the function is hardwired to UTC rather than the system's local clock. The fix is to use `date.today().isoformat()`.
